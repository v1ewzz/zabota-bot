# Процесс работы команды

Этот документ описывает, как команда работает с репозиторием `zabota-bot`.

## Ветвление

- `main` — основная ветка. Прямой пуш в `main` запрещён.
- Каждая задача разрабатывается в отдельной ветке.

### Названия веток

Используйте префиксы:

- `feature/` — новая функциональность;
- `fix/` — исправление ошибки;
- `docs/` — изменения в документации;
- `refactor/` — рефакторинг без изменений поведения;
- `chore/` — вспомогательные изменения (настройка, конфиги).

Примеры:

```bash
feature/bot-webhook-handler
feature/mini-app-main-screen
fix/database-connection-pool
docs/update-readme
```

### Создание ветки

```bash
git checkout main
git pull origin main
git checkout -b feature/your-feature-name
```

## Pull Request (PR)

1. Запушить ветку:

```bash
git push origin feature/your-feature-name
```

2. Создать Pull Request на GitHub:
   - Base: `main`
   - Compare: `feature/your-feature-name`

3. В описании PR указать:
   - что сделано;
   - как тестировать;
   - скриншоты (если есть UI-изменения).

4. Назначить минимум одного ревьювера из команды.

5. После аппрува — влить PR в `main`.

## Коммиты

Пишите осмысленные сообщения:

```text
feat: добавить webhook-обработчик для MAX
fix: исправить расчёт возраста ребёнка
docs: обновить README
refactor: вынести логику подбора в отдельный сервис
```

Избегайте сообщений вроде `fix`, `update`, `changes`.

## Работа с `.env` и секретами

- Никогда не коммитьте `.env` с реальными токенами, паролями и ключами.
- Используйте `.env.example` как шаблон.
- Токены храните:
  - локально в `.env` (не коммитится);
  - в GitHub Secrets (для CI/CD и деплоя).

## Код-ревью

Перед аппрувом проверьте:

- код компилируется и проходит локальные тесты;
- нет лишних `console.log`, закомментированных блоков;
- имена переменных и методов понятны;
- изменения соответствуют задаче.

## Синхронизация с `main`

Перед созданием PR актуализируйте ветку:

```bash
git checkout main
git pull origin main
git checkout feature/your-feature-name
git merge main
# или
git rebase main
```

Разрешите конфликты, если они возникли.

## Фиксация версии к дедлайну

Перед дедлайном:

1. Убедитесь, что всё важное влито в `main`.
2. Создайте тег:

```bash
git tag v1.0-hackathon
git push origin v1.0-hackathon
```

3. Зафиксируйте commit hash тега — это версия для сдачи.

После дедлайна изменения в код и презентацию вносятся только у финалистов.

## Контакты и коммуникация

- Основные обсуждения — в общем чате команды.
- Технические детали и код — в PR и issue на GitHub.
- Важные решения по архитектуре — фиксируйте в `docs/`.
