# SUBMISSION.md — ответы на вопросы ТЗ (проверка API)

## п.1. HTTPS-адрес доступного API

**https://piska-bobra.cloudpub.ru**

- Работающее приложение и документация доступны по этому адресу (cloudflared-туннель
  на локальный dev-стенд, docker compose). Перезапуск стенда не влияет на адрес.
- Swagger UI: `https://piska-bobra.cloudpub.ru/swagger-ui.html` → автоматический
  редирект на `/swagger-ui/index.html`.
- Машиночитаемая спецификация (live): `https://piska-bobra.cloudpub.ru/v3/api-docs`.

## п.2. OpenAPI-спецификация

- Файл: **`openapi.json`** (в корне репозитория) — снимок актуальной спецификации
  с живого стенда.
- OpenAPI 3.1.0 (springdoc-openapi 3.1.1, Spring Boot 4.1.1).
- **26 путей / 46 операций**, все `operationId` уникальны.
- `servers[0].url = "/"` — относительный базовый URL, спецификация не привязана
  к конкретному хосту.
- Живой источник спецификации всегда доступен на `https://piska-bobra.cloudpub.ru/v3/api-docs`.

## п.3. Тестовые учётные записи

**Не требуются.**

Авторизация в сервисе не реализована: в проекте нет `spring-boot-starter-security`,
JWT/RBAC/сессий. В спецификации объявлена схема `bearerAuth`, но это **задел на
будущее** — фактически она нигде не проверяется. Все проверки в DATA-API.yaml
выполняются анонимно (роль `anonymous`).

Команда сознательно не добавляет «фейковую» авторизацию ради формальности:
текущий продукт — подбор мер социальной поддержки для семей участников СВО
внутри мессенджера MAX, где идентификация пользователя выполняется платформой
MAX, и внедрять отдельную систему учётных записей преждевременно.

## п.4. Тестовые данные

Данные заполняются автоматически при старте (Flyway, в общей секции — регионы,
муниципалитеты, справочники; позднее — НПА, меры поддержки и правила подбора):

- 1 регион — Республика Татарстан, 1 муниципалитет — Казань;
- словари: семейное положение (Жена/Ребёнок/Родитель/Сам военнослужащий),
  военный статус, уровни образования, статусы оформления меры и др.;
- 16 НПА с реквизитами и ссылками, каталог мер поддержки и правила их привязки.

Разумеется, данных-«песочницы» мало для разнообразного подбора — поэтому
в репозитории подготовлен каталог **`test-data/`**:

- `test-data/reference/*.json` — снимки реальных ответов API (живые UUID);
- `test-data/payloads/user-create-full.json` — готовая анкета семьи с ребёнком
  (валидные ссылки на справочники);
- `test-data/payloads/user-create-minimal.json` — анкета только с обязательными
  полями;
- `test-data/payloads/user-update-status.json` — смена статуса оформления меры;
- `test-data/payloads/support-search.json` — параметры запроса подбора мер.

Порядок прогона описан в DATA-API.yaml (секции C-01 … C-10).

## п.5. DATA-API.yaml

Файл: **`DATA-API.yaml`** (в корне репозитория).

Структура соответствует п. 5.1–5.9 ТЗ: версия конфигурации, наименование решения,
базовый адрес API (единственный плейсхолдер в шапке — файл самодостаточен),
перечень проверок с описанием, метод+относительный путь, параметры запроса,
роль, ожидаемые статус-коды и ожидаемый формат ответа.

Охвачены:

1. **Справочные данные** (источник UUID): регионы, муниципалитеты по региону,
   справочники, уровни образования, каталог мер, НПА, правила подбора.
2. **Полный CRUD** административной записи (на примере региона): create/read/update/delete.
3. **Ядро сервиса — пользовательский сценарий**: анкета семьи → список → профиль →
   перезапуск алгоритма подбора → персональные результаты → детали записи →
   смена статуса оформления → выгрузка сводки → очистка данных.
4. **Негативные проверки HTTP-контракта**: 404 (путь и UUID), 405, 400 (тип
   параметра, JSON-тело, валидация), 415 (Content-Type), 422 (сознательное
   ограничение, см. ниже).

Известное ограничение (заявлено честно): `POST /api/users/{userId}/pdf-summary`
возвращает **422** — сводка в PDF генерируется, но фактическая отправка файла
в чат мессенджера MAX ещё в бэклоге (нужна точная сигнатура метода SDK
`max-bot-api-client`). Сервис отвечает корректным машинночитаемым форматом
ошибки, а не «притворяется», что файл отправлен.
