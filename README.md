# «Забота» — MAX Mini App + Spring Boot

«Забота» — сервис персонального подбора мер социальной поддержки для военнослужащих, участников СВО и их семей. Пользователь проходит анкету в мини-приложении MAX, после чего backend сохраняет профиль, выполняет подбор по набору правил и возвращает персональный список мер с описанием, документами, каналом обращения и ссылками на официальные источники.

## 1. Назначение решения

Сервис решает задачу навигации по мерам поддержки: вместо самостоятельного поиска по разным источникам пользователь указывает свой статус, регион, семейные обстоятельства и другие параметры, после чего получает отфильтрованный список доступных мер.

Основные возможности MVP:

- персональная анкета;
- подбор мер поддержки по правилам rules-engine;
- учёт региона и муниципалитета;
- учёт состава семьи и параметров детей;
- учёт статуса военнослужащего/участника СВО;
- учёт инвалидности, ранения, жилищного вопроса, газификации, беременности, дохода и занятости;
- карточки мер с размером/видом поддержки, документами, сроком и каналом оформления;
- переход к официальному источнику;
- личный кабинет с сохранённым результатом и статусами мер;
- печатная сводка результата.

## 2. Рабочий пользовательский сценарий

1. Пользователь открывает бота «Забота» в MAX.
2. В сообщении бота нажимает «Старт» и открывает мини-приложение.
3. Указывает имя и фамилию и подтверждает согласие на использование данных для подбора.
4. Проходит анкету: выбирает роль, статус военнослужащего/участника СВО, регион и муниципалитет, указывает детей и их параметры, отвечает на вопросы о здоровье, жилье, беременности, доходе и занятости.
5. После подтверждения анкеты frontend отправляет профиль в Spring Boot backend.
6. Backend сохраняет профиль в PostgreSQL и запускает повторный подбор персональных мер.
7. Пользователь получает список найденных мер, разделённых по получателю.
8. Открывает карточку меры, смотрит условия, документы, способ обращения и официальный источник.
9. В личном кабинете может менять статус меры и открыть сводку для печати/PDF.

```text

│   │   └── db/migration/             # Flyway V1...V26
│   ├── src/test/                    # unit/controller/service/mapper tests
│   ├── pom.xml
│   └── mvnw / mvnw.cmd
├── frontend/                        # React + Vite
│   ├── src/pages/                   # анкета, результаты, профиль, детали меры
│   ├── src/components/              # UI и карточки мер
│   ├── src/api/                     # REST-клиент, mock и rules-engine для mock-режима
│   ├── src/store/                   # локальное состояние и localStorage
│   ├── src/bridge/                  # интеграция с MAX WebApp API
│   ├── package.json
│   └── package-lock.json
├── database/                        # служебная папка проекта; миграции находятся в backend
├── docs/                            # документация команды
```

Важно: актуальные SQL-миграции находятся не в корневой `database/`, а в `backend/src/main/resources/db/migration/`. На текущей версии репозитория присутствуют миграции `V1`–`V26`, включая структуру БД, словари, меры поддержки, правила и связи с НПА.

## 4. Архитектура решения

Система состоит из трёх основных частей.

```text
                    ┌──────────────────────┐
                    │      MAX Bot         │
                    │ Long Polling API     │
                    └──────────┬───────────┘
                               │
                               ▼
                    ┌──────────────────────┐
                    │   Spring Boot API    │
                    │       Java 21        │
                    │                      │
                    │ Controllers          │
                    │ Services             │
                    │ Rules Engine         │
                    │ JPA / Flyway         │
                    └──────────┬───────────┘
                               │
                               ▼
                    ┌──────────────────────┐
                    │    PostgreSQL 16     │
                    │      database        │
                    └──────────────────────┘
                               ▲
                               │ REST /api
                               │
                    ┌──────────┴───────────┐
                    │   React Mini App     │
                    │       Vite           │
                    │                      │
                    │ Survey               │
                    │ Results              │
                    │ Account              │
                    │ Measure Details      │
                    │ Print summary        │
                    └──────────────────────┘
```

В production/runtime Docker-образ объединяет frontend и backend в одном контейнере: Nginx обслуживает собранный React frontend и проксирует `/api/` на Spring Boot, работающий внутри контейнера на `127.0.0.1:8080`. Наружу контейнер публикуется через порт `80`.

## 5. Backend

Backend реализован на Java 21 и Spring Boot 4.1.1.

Основные технологии и библиотеки:

- Spring Boot Web MVC;
- Spring Data JPA;
- Bean Validation;
- Flyway;
- PostgreSQL JDBC driver;
- MAX Bot API Client 0.5.0;
- Springdoc OpenAPI;
- JUnit/Spring Boot Test;
- Testcontainers для PostgreSQL-интеграционных тестов.

Основные слои:

- `controller` — REST API и HTTP-уровень;
- `service` — бизнес-логика;
- `entity` — JPA-сущности;
- `repository` — доступ к PostgreSQL;
- `mapper` — преобразование Entity/DTO;
- `dto` — объекты HTTP-запросов и ответов;
- `max` — обработка событий MAX;
- `db/migration` — версия схемы и начальные данные.

### Ключевые API

- `POST /api/users` — создание профиля;
- `GET /api/users/{id}/profile` — получение профиля вместе с детьми;
- `PUT /api/users/{id}` — обновление профиля;
- `PUT /api/users/{id}/profile` — обновление анкеты и повторный подбор;
- `DELETE /api/users/{id}` — удаление профиля;
- `POST /api/users/{id}/supports/search` — запуск персонального подбора по сохранённому профилю;
- `GET /api/users/{id}/supports` — сохранённые меры пользователя;
- `PATCH /api/users/{id}/supports/{userSupportId}` — изменение статуса/выбора/заметки по мере;
- `POST /api/supports/search` — прямой поиск мер по параметрам запроса;
- `GET /api/support-measures` и `GET /api/support-measures/{id}` — каталог мер;
- `/api/regions`, `/api/municipalities`, `/api/dictionaries`, `/api/npas` — справочные данные.

OpenAPI/Swagger UI подключён через Springdoc. Для локального запуска документация API доступна по стандартным адресам Springdoc: `/swagger-ui.html` и `/swagger-ui/index.html`.

## 6. Rules Engine и данные

Подбор выполняется по правилам, хранящимся в PostgreSQL. `SupportMatchingService` сопоставляет профиль пользователя с условиями мер поддержки и учитывает параметры пользователя и детей.

Поддерживаемые типы параметров включают, в частности:

- роль и статус военнослужащего;
- регион и муниципалитет;
- возраст и дата рождения;
- беременность;
- ранение и инвалидность;
- группа инвалидности;
- жилищный вопрос и необходимость газификации;
- доход и занятость;
- наличие детей;
- возраст ребёнка;
- образование ребёнка;
- класс;
- очную форму обучения;
- инвалидность ребёнка и её группу;
- дополнительные параметры профиля, предусмотренные backend-моделью.

Внутри одной группы правил условия проверяются совместно, а разные группы могут описывать альтернативные варианты соответствия. Размер меры может переопределяться конкретным сработавшим правилом через `amountOverride`.

## 7. Frontend

Frontend — React 18 + Vite.

Основные страницы:

- `Home` — создание/продолжение профиля;
- `Onboarding` — стартовый экран и согласие;
- `Survey` — анкета;
- `Results` — результаты персонального подбора;
- `MeasureDetail` — подробная информация о мере;
- `Account` — личный кабинет и статусы;
- `Print` — печатная сводка.

Анкета включает отдельный блок для детей. Для каждого ребёнка предусмотрены дата рождения, образовательный уровень, класс для школьника, очная форма обучения для соответствующих уровней и данные об инвалидности.

Состояние профиля, результатов и статусов мер сохраняется в `localStorage`. Используется версия ключей `zabota:v4` с поддержкой чтения предыдущей версии `zabota:v3`.

Frontend умеет работать в двух режимах:

- реальный backend — `VITE_USE_MOCK=false`;
- локальный mock-режим — `VITE_USE_MOCK=true`.

Для реального запуска через общий Docker-образ `VITE_API_BASE_URL` оставляется пустым: запросы идут на тот же origin `/api`, а Nginx передаёт их Spring Boot.

## 8. MAX и внешние сервисы

Основная внешняя интеграция MVP — MAX Bot API.

Бот использует Long Polling и обрабатывает события:

- запуск бота;
- сообщения;
- callback-кнопки.

Кнопка «Старт» в сообщении бота открывает Web App/мини-приложение MAX. Для работы этой части нужен зарегистрированный бот MAX и токен.

В карточках мер могут использоваться внешние официальные ссылки, например на Госуслуги, СФР, ФНС, банки и другие организации. Это ссылки для перехода пользователя, а не прямые API-интеграции.

Прямые программные интеграции с ЕГИССО, СФР, ФНС и другими государственными информационными системами в текущем MVP не реализованы. Данные каталога и условий поставляются через собственные таблицы PostgreSQL и Flyway seed-миграции.

## 9. Запуск локальной версии через Docker

### Требования

Нужны:

- Docker Desktop / Docker Engine с Compose;
- доступ к интернету для первой сборки Docker image;
- токен зарегистрированного MAX-бота;
- имя/username MAX-бота для открытия Web App.

### Настройка переменных окружения

В корне проекта создайте `.env`.

Минимальный набор для текущего Docker Compose:

```dotenv
DB_URL=jdbc:postgresql://db:5432/zabota
DB_USERNAME=zabota_user
DB_PASSWORD=change_me

MAX_BOT_MODE=longpolling
MAX_BOT_TOKEN=your_max_bot_token
MAX_BOT_USERNAME=your_max_bot_username
```

`SERVER_PORT` можно не задавать: backend использует `8080` по умолчанию.

Для production/frontend с общим Nginx `VITE_API_BASE_URL` оставляется пустым, а `VITE_USE_MOCK=false`.

Не помещайте реальные токены и пароли в Git.

### Одна команда запуска

После создания `.env` весь локальный стенд запускается одной командой:

```bash
docker compose up --build
```

Команда собирает frontend, backend и общий runtime-образ, затем запускает приложение и PostgreSQL.

Для фонового запуска:

```bash
docker compose up -d --build
```

### Порты

- `http://localhost:8080` — входная точка приложения; Docker публикует внутренний Nginx-порт `80`;
- `5432` — PostgreSQL внутри compose-сети доступен приложению как `db:5432`.

PostgreSQL хранит данные в Docker volume `db_data`.

## 10. Порядок проверки после запуска

1. Выполнить `docker compose up --build`.
2. Проверить состояние контейнеров:

```bash
docker compose ps
```

Ожидаются запущенные сервисы `app` и `db`. `db` должен пройти healthcheck PostgreSQL.

3. Открыть в браузере:

```text
http://localhost:8080
```

4. Проверить стартовый экран и переход в анкету.
5. Заполнить тестовый профиль: роль, статус, регион, муниципалитет, доход и занятость.
6. В блоке детей добавить ребёнка, указать дату рождения, образование и, при необходимости, класс/очную форму/инвалидность.
7. Нажать «Подобрать меры».
8. Проверить, что frontend обращается к backend и появляются карточки найденных мер.
9. Открыть одну меру и проверить наличие описания, размера/вида поддержки, документов и канала обращения.
10. Проверить переход к личному кабинету и изменение статуса меры.
11. Открыть «Сводка» и проверить формирование печатного представления.

### Проверка API

Для быстрой проверки backend без интерфейса можно запросить справочник регионов:

```bash
curl http://localhost:8080/api/regions
```

После первого запуска Flyway автоматически применяет миграции `V1`–`V26` в базе `zabota`.

Остановить контейнеры без удаления данных БД:

```bash
docker compose down
```

Запустить существующий стенд снова:

```bash
docker compose up -d
```

Пересобрать после изменения исходников:

```bash
docker compose build --no-cache
docker compose up -d
```

Не используйте `docker compose down -v`, если необходимо сохранить PostgreSQL volume `db_data`.

Для просмотра логов:

```bash
docker compose logs --tail=200 app
```

## 13. Данные и хранение

Основное постоянное хранилище backend — PostgreSQL.

В БД хранятся:

- профили пользователей;
- дети пользователей;
- регионы и муниципалитеты;
- значения справочников;
- меры поддержки;
- правила подбора;
- НПА и связи НПА с мерами;
- персональные меры пользователя и их статусы.

Изменение схемы и начальное наполнение выполняются Flyway-миграциями. Hibernate работает в режиме `ddl-auto=validate`, поэтому структура БД не генерируется автоматически.

Frontend дополнительно хранит локальное состояние профиля, результатов и статусов в браузере через `localStorage`.

## 15. Ожидаемое поведение при демонстрации

После запуска пользователь должен:

- открыть приложение в MAX;
- пройти анкету без ручного редактирования БД;
- получить персональный набор мер;
- открыть детальную карточку меры;
- увидеть документы и способ обращения;
- сохранить профиль и результат;
- открыть личный кабинет;
- изменить статус меры;
- сформировать сводку.

Подбор является предварительным: окончательное решение о наличии права, размере и порядке предоставления конкретной меры принимает уполномоченный орган.

## 16. Известные ограничения

- В MVP нет полноценной пользовательской авторизации и JWT-аутентификации REST API.
- Интеграции с государственными системами не являются прямыми API-интеграциями; используются собственные данные каталога и ссылки на официальные источники.
- Кнопка заявки в МФЦ в текущем backend не реализует отправку реальной заявки.
- Часть региональных записей и отдельных мер в seed-данных помечена как демонстрационная.
- Для работы бота нужен зарегистрированный MAX-бот и корректный токен.
- Одновременный запуск нескольких экземпляров одного MAX-бота в режиме Long Polling не предназначен для общей локальной/production-схемы: экземпляры могут конкурировать за получение обновлений.
