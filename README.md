# «Забота» — MAX Mini App + Spring Boot

«Забота» — сервис персонального подбора мер социальной поддержки для военнослужащих, участников СВО и их семей.

Пользователь описывает свою ситуацию через анкету: указывает семейные обстоятельства, статус военнослужащего, регион и муниципалитет, сведения о детях, жилье, здоровье, доходе и дополнительные потребности. Backend сохраняет профиль, применяет правила подбора и возвращает персональный список мер поддержки с условиями, документами, способом обращения и официальными источниками.

Проект реализован как MAX-бот с открываемым из бота Mini App, единый web-интерфейс с REST API и PostgreSQL.

## 1. Назначение решения

Основная задача «Заботы» — сократить количество ручного поиска информации о мерах социальной поддержки.

Вместо самостоятельного просмотра различных источников пользователь один раз описывает свою ситуацию. Система сопоставляет профиль с условиями доступных мер и формирует персональную подборку.

Основные возможности:

- персональная анкета пользователя;
- учет семейной ситуации;
- учет статуса военнослужащего или участника СВО;
- учет региона и муниципалитета;
- учет детей и их возраста;
- учет образования ребенка;
- учет инвалидности и ранения;
- учет жилищного вопроса и необходимости газификации;
- учет дохода и занятости;
- учет дополнительных потребностей;
- алгоритмический подбор мер поддержки;
- отображение размера или вида поддержки;
- отображение условий получения;
- отображение необходимых документов;
- отображение места и способа обращения;
- переход к официальному источнику;
- личный кабинет;
- сохранение персональных мер и их статусов;
- формирование PDF-сводки результатов и отправка ее в чат MAX;
- локальный mock-режим frontend для разработки.

Подбор носит справочный характер. Окончательное решение о наличии права, размере и порядке предоставления конкретной меры принимает уполномоченный орган.

## 2. Рабочий пользовательский сценарий

Основной сценарий:

1. Пользователь открывает бота «Забота» в MAX.
2. Нажимает «Старт» и открывает Mini App.
3. Указывает имя и фамилию и подтверждает согласие на обработку данных.
4. Заполняет анкету.
5. Указывает:
   - семейную роль;
   - статус военнослужащего;
   - регион;
   - муниципалитет;
   - сведения о детях;
   - состояние здоровья;
   - жилищный вопрос;
   - необходимость газификации;
   - доход и занятость;
   - дополнительные потребности.
6. Нажимает «Подобрать меры поддержки».
7. Frontend отправляет данные в Spring Boot API.
8. Backend сохраняет профиль в PostgreSQL.
9. Rules Engine сопоставляет профиль пользователя с правилами мер поддержки.
10. Найденные меры сохраняются как персональные записи пользователя.
11. Frontend получает персональный список мер.
12. Пользователь открывает карточку конкретной меры и получает:
    - описание;
    - размер или вид поддержки;
    - получателя;
    - условия;
    - необходимые документы;
    - куда обращаться;
    - порядок оформления;
    - правовое основание;
    - официальный источник.
13. В личном кабинете пользователь может отслеживать выбранные меры и их статусы.
14. Сводку результатов можно сформировать в PDF и отправить в чат MAX.

## 3. Демонстрационный сценарий

Для демонстрации используется сценарий семьи участника СВО.

Пример:

- заявитель — супруга военнослужащего;
- статус военнослужащего — мобилизованный;
- в семье двое детей;
- возраст детей — 16 и 7 лет;
- семье требуется газификация;
- пользователь планирует открыть собственный бизнес.

Этот сценарий позволяет показать одновременно работу нескольких групп правил: статус военнослужащего, семейный состав, возраст детей, региональные условия, жилищную потребность и дополнительные условия.

В Docker используется единый runtime-контейнер:

- Nginx обслуживает собранный React frontend;
- Nginx проксирует `/api/` на Spring Boot;
- Spring Boot работает внутри контейнера на `127.0.0.1:8080`;
- наружу контейнер публикуется через порт `80`;
- PostgreSQL запускается отдельным контейнером;
- данные PostgreSQL сохраняются в Docker volume `db_data`.

## 6. Backend

Backend реализован на Java 21 и Spring Boot 4.1.1.

Основные зависимости:

- Spring Boot Web MVC;
- Spring Data JPA;
- Spring Boot Flyway;
- Flyway PostgreSQL;
- Bean Validation;
- PostgreSQL JDBC;
- MAX Bot API Client 0.5.0;
- MAX Bot API Jackson 0.5.0;
- MAX Bot API Long Polling 0.5.0;
- MAX Bot API Spring Boot 0.5.0;
- OpenPDF 1.3.42;
- Springdoc OpenAPI 3.1.1;
- JUnit / Spring Boot Test;
- Testcontainers PostgreSQL.

Файлы, фиксирующие используемые библиотеки и версии, лежат в корне репозитория:

| Стек | Файл | Что фиксирует |
| --- | --- | --- |
| Frontend (npm) | `package-lock.json` | копия `frontend/package-lock.json` — 113 пакетов с точными версиями |
| Backend (Maven) | `dependencies.txt` | все 156 разрешённых артефактов с версиями и scope: `группа:артефакт:тип:версия:scope` |

`frontend/package-lock.json` — источник истины для npm: его использует `npm ci` в
`Dockerfile` и в локальной разработке фронта, поэтому он остаётся рядом с
`frontend/package.json`. Корневой `package-lock.json` — его копия для проверяющего.
Если локфайл фронта изменился, синхронизируйте копию:

```bash
cp frontend/package-lock.json package-lock.json
```

`dependencies.txt` сгенерирован из `backend/pom.xml` и включает транзитивные
зависимости, версии которых наследуются от `spring-boot-starter-parent 4.1.1`
(в `pom.xml` 14 из 20 прямых зависимостей идут без явной версии).
Перегенерация:

```bash
cd backend
./mvnw dependency:list -DincludeScope=test -DoutputFile=../dependencies.txt -DappendOutput=false
```

Инструменты: Java 21, Maven 3.9.16, Node.js 20, PostgreSQL 16.

Основные слои backend:

- `controller` — HTTP REST API;
- `service` — бизнес-логика;
- `repository` — работа с БД;
- `entity` — JPA-сущности;
- `dto` — запросы и ответы API;
- `mapper` — преобразование Entity/DTO;
- `max` — интеграция с MAX;
- `exception` — единая обработка ошибок;
- `db/migration` — схема и seed-данные.

Hibernate работает с `ddl-auto=validate`. Структура БД создается и изменяется только через Flyway.

## 7. Frontend

Frontend реализован на React 18 и Vite.

Основные страницы:

- `Home` — старт и создание профиля;
- `Survey` — основная анкета;
- `Questionnaire` — дополнительный маршрут анкеты;
- `Results` — результаты подбора;
- `MeasureDetail` — подробная информация о мере;
- `Account` — личный кабинет;
- `Print` — сводка результатов.

Frontend использует REST API через единый клиент.

При работе в MAX используется bridge для Mini App API, включая:

- определение среды MAX;
- получение launch/init context;
- получение данных пользователя MAX;
- открытие внешних ссылок;
- управление кнопкой «Назад»;
- haptic feedback.

Состояние профиля и часть пользовательского состояния сохраняются в `localStorage`.

Для разработки предусмотрен mock-режим:

```text
VITE_USE_MOCK=true
```

Основной режим проекта:

```text
VITE_USE_MOCK=false
```

## 8. Rules Engine

Персональный подбор реализован на backend.

Условия мер хранятся в PostgreSQL в виде правил.

В правилах используются:

- роль пользователя;
- статус военнослужащего;
- регион;
- муниципалитет;
- возраст;
- дата рождения;
- беременность;
- ранение;
- инвалидность;
- группа инвалидности;
- жилищная проблема;
- газификация;
- доход;
- занятость;
- наличие детей;
- возраст ребенка;
- образование ребенка;
- класс;
- очная форма обучения;
- инвалидность ребенка;
- дополнительные параметры профиля.

Логика группировки правил:

- условия внутри одной `condition_group` проверяются совместно;
- разные группы могут представлять альтернативные варианты соответствия;
- при срабатывании конкретного правила может использоваться `amountOverride`.

Таким образом, подбор не является простым фильтром по одному параметру: профиль пользователя сопоставляется с набором условий конкретных мер.

## 10. MAX-интеграция

Бот работает через MAX Bot API в режиме Long Polling.

Используются события:

- `BOT_STARTED`;
- `MESSAGE_CREATED`;
- `MESSAGE_CALLBACK`.

Стартовый сценарий:

```text
Пользователь
    ↓
Открывает MAX-бота
    ↓
Нажимает «Старт»
    ↓
Получает кнопку открытия Mini App
    ↓
Заполняет анкету
    ↓
Mini App → REST API
    ↓
Spring Boot → PostgreSQL
    ↓
Rules Engine
    ↓
Персональный список мер
```

Для работы бота необходим зарегистрированный MAX-бот и токен.

Реальные токены, пароли и ключи не хранятся в Git.

## 15. Локальный запуск через Docker

### Требования

Необходимы:

- Docker Desktop или Docker Engine;
- Docker Compose;
- доступ к интернету для загрузки базовых Docker images;
- токен MAX-бота для проверки MAX-интеграции.

### Переменные окружения

В корне проекта создайте `.env` на основе `.env.example`.

Минимальная конфигурация:

```dotenv
DB_URL=jdbc:postgresql://db:5432/zabota
DB_USERNAME=zabota_user
DB_PASSWORD=changeme

MAX_BOT_TOKEN=your_max_bot_token_here
MAX_BOT_MODE=longpolling
MAX_BOT_USERNAME=your_bot_user_name

VITE_BACKEND_URL=http://localhost:8080
```

Важно:

- `.env` не должен попадать в Git;
- реальные токены и пароли нельзя размещать в README;
- `.env.example` содержит только безопасные шаблонные значения.

### Запуск

Одна команда:

```bash
docker compose up --build
```

Фоновый запуск:

```bash
docker compose up -d --build
```

Docker:

1. собирает React frontend;
2. устанавливает frontend-зависимости через `npm ci`;
3. собирает Java backend;
4. создает единый runtime image;
5. запускает Nginx;
6. запускает Spring Boot;
7. запускает PostgreSQL;
8. ожидает прохождения healthcheck PostgreSQL;
9. после подключения Spring Boot применяет Flyway-миграции.

### Порты

```text
http://localhost:8080
```

Основная точка входа локального приложения.

PostgreSQL:

```text
localhost:5432
```

Внутри Docker Compose backend обращается к БД:

```text
jdbc:postgresql://db:5432/zabota
```

Сервис не использует прямые программные интеграции с ЕГИССО, СФР, ФНС или другими государственными информационными системами.

Официальные внешние сайты, указанные в карточках мер, используются как источники информации для пользователя и не являются backend API-интеграциями.

## 23. Известные ограничения

Текущая версия является MVP.

Ограничения:

- полноценная пользовательская JWT-аутентификация REST API не реализована;
- каталог мер и правила являются собственной базой данных проекта;
- нет прямой API-интеграции с государственными информационными системами;
- отдельные данные каталога могут иметь демонстрационный характер;
- окончательное право на меру определяется уполномоченным органом;
- часть действий, например реальная подача заявления в МФЦ, не выполняется автоматически через API;
- для MAX-бота требуется зарегистрированный бот и корректный токен;
- один экземпляр MAX-бота должен использоваться в режиме Long Polling без конкурирующих экземпляров, получающих те же обновления.

## 28. Ответы на вопросы проверки API

### п.1. HTTPS-адрес доступного API

```text
https://zabota-bot-viewzz.amvera.io
```

- рабочее приложение и документация доступны по этому адресу;
- Swagger UI: `https://zabota-bot-viewzz.amvera.io/swagger-ui/index.html`;
- машиночитаемая спецификация: `https://zabota-bot-viewzz.amvera.io/v3/api-docs`.

### п.2. OpenAPI-спецификация

- файл `openapi.json` в корне репозитория — снимок спецификации с живого
  стенда;
- OpenAPI 3.1.0 (springdoc-openapi 3.1.1, Spring Boot 4.1.1);
- 26 путей / 46 операций, все `operationId` уникальны;
- `servers[0].url` = `/`, то есть спецификация не привязана к конкретному хосту.

### п.3. Тестовые учётные записи

**Не требуются.** Авторизация в сервисе не реализована: в проекте нет
`spring-boot-starter-security`, JWT/RBAC и сессий. В спецификации объявлена
схема `bearerAuth`, но она нигде не проверяется и является заделом на будущее —
все проверки выполняются анонимно, роль `anonymous`.

Команда не добавляла «фейковую» авторизацию ради формальности: продукт работает
внутри мессенджера MAX, где идентификация пользователя выполняется платформой
MAX на стороне Mini App, поэтому отдельная система учётных записей пока не
нужна.

### п.4. Тестовые данные

Справочники и каталоги заполняются автоматически при старте (Flyway). Для
разнообразного подбора в репозитории подготовлен каталог `test-data/` —
снимки реальных ответов API и готовые payload-ы. Порядок работы с ними описан
в разделе 14.

### п.5. DATA-API

Файл `DATA-API.yaml` в корне репозитория: 29 проверок (справочники, CRUD
справочной записи, сквозной пользовательский сценарий, негативные проверки
HTTP-контракта). Единственный параметр для смены стенда — `BASE_URL` в шапке
файла; по умолчанию подставлен адрес из п.1.
